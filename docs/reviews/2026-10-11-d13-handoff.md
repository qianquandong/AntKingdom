## 实现要求

1. 先加入仅 Debug 可见的结构化诊断：事件顺序号、会话/进程标识、scenePhase、墙钟、单调时钟、最后有效前台帧、离开基准、当前高水位、保存原因/结果、isInBackground、结算起止与实际收益、总结是否呈现。每次复现导出环形日志，避免每帧无限写盘。不得记录设备标识、购买票据或账号数据，发行配置必须剔除诊断入口。
2. 明确“开始离线 / 结算 / 恢复在线 / 保存”的顺序与唯一负责人；同一离开区间恰好结算一次。有证据后选择修复，记录根因与为何覆盖失败时序。
3. **保存时间与离线起点不得互相覆盖**。保存操作可以记录持久化时间，但恢复前的自动保存或延迟回调不能吃掉尚未结算的后台区间。增加确定性时序测试，不依赖碰运气重跑。
4. 保持 PRD：离线效率 25%；最多模拟 1 小时且封顶适用于所有时钟；离线不使用 Foraging Boost；广告展示暂停有效前台步进；时间回拨不出现负收益或重复结算。短离开不足 60 秒仍要正确结算，只是不弹 Welcome Back。
5. 核心 target AntKingdom 与发行 target CrumbKingdom 共用修复后的生命周期规则。不要只修核心 UI 而遗漏 CampaignModel。
6. 不得用删除/跳过失败用例、仅改为检查调试探针、增加等待时间或不停 rerun 来宣布 D-13 修复。诊断能补充证据，不能代替对最终 Food、存档与可见离线总结的断言。
7. 更新 M2 报告、执行看板、已知缺陷和 QA 对应项；关联修复 commit、PR、CI run + attempt。
