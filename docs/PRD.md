# 一厘米蚂蚁王国 · Crumb Kingdom

版本：v0.2，2026-10-11。状态：核心验证版需求与可执行数值基准，尚无可玩的 iPhone 客户端。

文档、开发说明和评审使用中文；所有玩家可见名称、按钮、提示、通知、错误信息使用英文，以附录 A 为准。Crumb Kingdom 是工作名，公开发行前另做名称检索。

## 1. 产品目标与本次取舍

一句话体验：玩家亲手挖开泥土，看到蚂蚁接通食物、绕开堵点，并把食物更快地搬进地下王国。

首版只回答三个问题：点击挖土是否舒服；玩家能否理解自己改变了运输；改善之后是否愿意继续观察和尝试。目标人群是喜欢点击、放置和微缩生态观察的 iPhone 玩家。竖屏、单手操作，首轮测试约 10–15 分钟。

本版是供小规模用户测试的核心验证版，不是完整商业发行版。原 v0.1 的四地层、八天成长、完整商店与广告方案进入 [后续路线图](ROADMAP.md)。旧稿保留在 [历史提交](https://github.com/qianquandong/AntKingdom/blob/3bd2062033cb5c2fcc1ff275c486cbee5e3a67df/docs/PRD.md)，不再作为当前实现依据。

| 项目 | P0 必须实现 | 暂缓 |
|---|---|---|
| 地图 | 一张 9×9 地下地图，加一行地面 | 四地层、第二世界、根系开采、最终宝石 |
| 操作 | 挖土、长按、选中目标、移动一个仓库 | Dig 升级、工具链、批量自动挖掘 |
| 蚁群 | 5–24 只，自动搬运，两个孵化槽，孵化暂停开关 | 职业分配、兵蚁、装备、Queen 等级树 |
| 建造 | 一个固定 Queen Chamber，一个可移动 Pantry | 建造队列、升级等待、拆除退款、多仓库 |
| 食物 | 两个固定补给点轮流补充，一个树液根、地面兜底 | 在未挖掘区域随机生成事件、多资源经济 |
| 反馈 | 路线、繁忙格、往返耗时、预计产量、仓满提示 | 战斗、天气、灾害、社交、排行榜 |
| 保存 | 本机存档、恢复、最多一小时离线结算 | 账号、云存档、服务端经济、防作弊服务 |
| 商业化 | 无付费、无广告 SDK | 广告、IAP、订阅、付费建造队列 |

首版允许触达容量与人口上限。到达上限是本轮试验结束点之一，不能据此宣称已验证日留存或长期内容消耗。补给可重复刷新，只解决“挖完地图后事件永久消失”的问题；它不替代成长内容和食物消耗系统。

## 2. 核心循环与首局

核心循环：挖开相邻土格 → 接通食物 → 蚂蚁搬运 → Food 自动孵化新蚂蚁或由玩家攒下建仓 → 观察路线和拥堵 → 挖捷径、旁路或移动 Pantry → 对比运输反馈。

### 2.1 首局步骤

时间是试玩观察目标，不是脚本承诺，实际触发以状态为准。

1. 进入时已有 5 只搬运工、0 Food、地面兜底收入。镜头显示 Queen Chamber 与 Cookie Crumb。提示 `tutorial.dig`，高亮可挖边界，不出现商店。
2. 向 Cookie Crumb 挖出连接；源从地面切换到饼干。用 `feedback.connected` 告知接通，短暂高亮真实运输路线。
3. 食物满 20 时自动进入孵化，30 秒后新增一只。点 Queen Chamber 可以暂停新增孵化订单；已有卵继续完成，允许攒下 50 Food 建仓。
4. 引导开出一个合法 2×2 区域，建造 Pantry。展示移动入口和摆放预览；非法位置不能确认、不扣 Food。
5. 引导玩家比较调整前后的路线。只在冻结人口与源之后预计产量确实增加时显示 `feedback.route_better`；没有增益则正常确认挖掘/移动，不编造“优化成功”。
6. 给玩家自由尝试时间，观察下一次补给点变化。到人口和容量上限后显示 `goal.prototype_complete`，仍可挖土与移动仓库；重置需二次确认。

不强制所有首局都出现拥堵。低人口或很短的路线可能没有繁忙格；旁路规则的验收使用第 6 章固定场景，并在单独试玩中观察玩家是否能自行处理它。

### 2.2 点击与交互

- 每个 Soil 格固定 3 次有效点击；长按每秒 5 次，手动点击逻辑上限每秒 8 次。没有体力、点击货币或 Dig 等级。
- 仅能挖与现有通路四邻接的 Soil。镜头拖动与挖掘手势互斥；在 UI 上的触摸不能穿透地图。
- 三次命中分别呈现裂纹、碎屑、开通。轻触觉可关闭；音效可关闭。一次完成一格时更新通路，不逐帧重新规划。
- 点源展示余量、连接状态、Trip、Food/min；点 Queen Chamber 展示蚂蚁/卵及孵化开关；点 Pantry 展示移动入口。
- 建造/移动模式显示 2×2 预览、确认与取消。取消无状态变化。移动不收费，原位置保留通路。

## 4. 运输与拥堵：唯一计算口径

### 4.1 图、距离与时间

运输只沿四邻接的已挖通路、入口和房间格行走。有限源与树液根的装货点是其相邻且已连通的通路格；地面源使用入口。卸货点是 Queen Chamber 与 Pantry 的任意占地格。

一条路径包含装货点和卸货点；`L = max(1, 路径格数 − 1)`，单位为格。若同一通路格同时可装卸，仍按一格服务距离计，防止零距离导致无限产量。装卸点不计入路段拥堵，它们的服务耗时已单独计入。

`Trip` 始终表示**装货 → 送达 → 返回装货点的完整周期**，包括装卸，不是单程移动时间。视觉与经济均使用同一周期；收入采用连续、可存小数的平均流量账本，搬运粒子和到达动画不再二次加 Food。

| 参数 | 首版值 | 单位 |
|---|---:|---|
| `v` | 2 | 格/秒 |
| `b` | 2 | Food/每只蚂蚁的完整运输周期 |
| 装货时间 | 2 | 秒 |
| 卸货时间 | 1 | 秒 |
| `C` | 8 | 每个中间通路格的搬运工服务预算 |
| 地面额外搜寻时间 | 12 | 秒/周期，仅地面兜底源 |

### 4.2 共享负载与拥堵

本版使用可解释的“路线分配负载”，不模拟瞬时物理排队，也不再使用 `n / L` 密度。所有路线上被分配的蚂蚁，共同占用经过的中间格；往返合计每只只算一次预算。

```text
load[c] = 所有经过中间格 c 的路线上的蚂蚁数量之和
overload[r] = Σ max(0, load[c] / C − 1)     # c 遍历路线 r 的中间格
T[r] = 2 × (L[r] + overload[r]) / v + 3 + source_extra_seconds
Food_per_second = Σ n[r] × b / T[r]
Food_per_minute = 60 × Food_per_second
```

某格 `load > 8` 才显示繁忙橙色，`load <= 8` 显示正常。颜色之外同时用队列小图标/线型表示，避免只依赖颜色。相交或合流的路线必须共享 load，不能各自独立计算。末端装卸口暂不模拟排队，这是验证版简化边界；商业版增加服务瓶颈前必须另做基准。

例如 7 只蚂蚁走一格路径：没有中间拥堵格，T=4 秒，Food/min=7×2/4×60=210。不会再因为 `7/1` 人为降低到 176.84。

### 4.3 路线选择与分流

1. 对每个源从所有可用装货点到所有卸货点做 BFS，取最短主路径。起点按 y、x 排序，邻接顺序固定为上、左、右、下。
2. 逐一禁用主路径的非终点格，重新 BFS 生成替代路径。去重后按路径长度、坐标序列排序，最多保留 4 条。允许发现另一装货口；不宣称枚举所有路线。
3. 初始把该源的蚂蚁分到主路径。逐一试算从一条候选路线移出一只、放到同源另一条路线的结果，每次都重算全体源共享负载与总 Food/s。
4. 接受严格增加总产量最多的一个调整；增益必须大于浮点容差 1e-10。相同增益保留遍历中先出现的方案。没有改善则结束；最多 256 次调整，超过视为开发错误并记录，不静默当成功。
5. 每个相同状态都从相同初值求解，结果一致。取消旧 15% 改道门槛，避免有用旁路永远不启用。逻辑分配立即生效，动画平滑过渡，不逐秒在旧新路径之间翻转。

这是有界候选集上的局部改进，不能证明全局最优。客户端必须和 Python 基准一致；以后升级寻路器时，同时更新规则、固定场景与验收结果。

只在挖通格、建/移仓、蚂蚁数量变化、源耗尽/补充时重算；暂停孵化本身不改路线。库存满时无需重新求路，暂停入库即可。路径缓存不能跨地图、卸货点、源和人口变化复用。

### 4.4 首版源分配

全体成年蚂蚁服务一个源，优先级：**已连接且有存量的固定补给 > 已连接树液根 > 地面兜底**。同级按无拥堵周期较短者、源 ID 字典序选取。没有连接就不能采集，不允许脚本自动挖通。

暂不开放 Jobs 或源优先级设置。运输求解器支持多个需求并测试共享负载，供后续扩展；首版游戏不暴露该系统。源耗尽后下一逻辑步切到可用源；尚未连接的新补给保留存量，不阻断兜底采集。

### 4.5 满仓与展示

每步先算预计产量，再限制为源剩余量和仓储剩余空间；**只对实际入库部分扣减有限源**。满仓时源和库存保持原值，显示 `state.storage_full`，搬运表现转为待命。孵化消耗腾出空间后，下一步恢复搬运。

预计 Food/min 展示当前网络不受库存限制时的能力；满仓时另外显示状态，不能把实际零入库误报为路线变慢。Trip 按当前所选源的已分配蚂蚁加权平均周期展示（无活跃路线时用 `state.no_route`），不是把多条路线耗时相加。只显示已分配蚂蚁的路线。

## 5. 经济、刷新与存档

### 5.1 固定首版数值

| 项目 | 数值/行为 |
|---|---|
| 初始 Food / 成年蚂蚁 | 0 / 5 |
| 人口上限 | 24，成年蚂蚁与孵化中的卵一起占人口 |
| 孵化成本 / 时间 / 槽位 | 20 Food / 30 秒 / 2 |
| 初始孵化设置 | 开启；有钱且有空槽即下单 |
| 暂停孵化 | 只停止新订单，已有卵继续完成；无退款 |
| Queen Chamber 容量 | 100 Food |
| Pantry 成本 / 额外容量 | 50 Food / 1000 Food |
| Cookie Crumb 初始存量 / 补充量 | 600 / 600 Food |
| Sugar Drop 初始存量 / 补充量 | 0 / 150 Food |
| Sap Root / 地面 | 无限；必须遵守真实路线与源优先级 |
| 固定补给刷新间隔 | 两处有限补给均空后 60 秒 |
| 离线效率 / 计时上限 | 在线流量的 25% / 一小时 |

Food 逻辑保留双精度小数，不逐步取整；UI 库存向下取整，预计产量保留一位小数，Trip 保留一位小数。孵化按真实余额是否达到 20 判断。

### 5.2 补给刷新

开局只有 Cookie Crumb 有存量。两处都空后开始倒计时 60 秒；第一轮给 Sugar Drop 补 150，下一轮给 Cookie Crumb 补 600，之后交替。只有两个都空才推进倒计时；不因为仓满、离开画面或挖完地图直接扣粮。

补给占地不依赖未挖 Soil；刷新不扩张地图、不破坏通路与房间。空补给显示标记和等待状态，来货用 `event.food_arrived`。若未连接的 Sugar Drop 还有粮，下一轮刷新等待它被消耗；玩家仍可从地面或树液根得到食物。

### 5.3 统一时间推进与离线

经济基准步长 0.25 秒，在孵化完成和刷新到期的边界切短步长。每步顺序：按步初路线入库 → 推进已有卵并完成孵化 → 尝试新的孵化订单 → 推进已开始的补给空置计时 → 更新时间。刚在本步耗尽的补给，从下一步开始空置计时，误差最多一个基准步长。

离线读取保存状态，令 `dt = clamp(当前时间 − 保存时间, 0, 3600)`，逐步执行同一状态机；只把运输流量乘 0.25。孵化与补给计时按这段被封顶的实际秒数推进，不额外乘 0.25。超过一小时的剩余时间全部忽略，包括孵化和补给；负时间按零处理。工具底层拒绝负值/非有限输入，客户端时间适配层负责钳制。

不能先完整在线模拟，再把最后的库存乘 25%；孵化支出、人口变化、源切换与仓储封顶会改变后续状态。离线结果同时记录实际搬入 Food 和库存净变化；玩家提示用 `offline.summary` 的实际搬入值，不能把孵化支出漏算，也不能承诺余额只增不减。

保存字段：版本号、地图 ID、已挖格与未完成格点击数、Food、蚂蚁数量、每个卵的剩余时间、孵化开关、Pantry 占地、每个有限源余量、补给倒计时与下一个补给 ID、累计逻辑时间、最后保存时间、音效/触觉设置。路线与缓存从上述状态重建，不单独信任缓存。

客户端在关键操作后和进入后台时原子保存，写临时文件后替换；启动校验非法占地、负资源、超人口等状态。保存损坏先尝试最近有效备份，再提供英文错误与重置入口。本仓库目前验证数值逻辑，不代表已实现 iOS 存档或后台生命周期。

## 6. 可执行基准与验收

### 6.1 三个冻结变量的运输对照

权威数据：[design/transport_cases.json](../design/transport_cases.json)。每个场景固定人口、速度、载量和源；无孵化、无仓满、无源耗尽。坐标夹具表示可通行路线和卸货边界，不是完整关卡；Pantry 的实际 2×2 放置与移动另有地图状态测试。

| 场景 | 唯一改变 | 调整前 Food/min | 调整后 Food/min | 增益 |
|---|---|---:|---:|---:|
| 缩短路线 | 5 只，L 从 6 到 4 | 66.666667 | 85.714286 | 28.571429% |
| 平行旁路 | 16 只，从一条 L=8 路线到两条等长路线 | 106.666667 | 174.545455 | 63.636364% |
| 移动卸货点 | 7 只，L 从 3 到 1 | 140.000000 | 210.000000 | 50.000000% |

手算旁路场景：原路径有 7 个中间格，各承载 16 只，overload=7，T=18 秒。挖开旁路后两路仅共用装卸端点，各分配 8 只，overload=0，T=11 秒。分配总数保持 16；繁忙格负载从 16 降至 8。

开发调试入口可加载这三组固定状态；不把调试入口做进正式玩家菜单。客户端接入时，应重放同样输入并与 Python 输出比对，不能仅凭动画“看起来分流了”验收。

### 6.2 实际地图固定回放

工具的 600 秒回放按确定时间完成指定挖格，并在余额足够时建仓。它是回归测试脚本，不模拟真实点击速度、用户选择或付费行为：

- 30 秒挖开 (2,4)、(2,5)、(2,6)，接通 Cookie Crumb。
- 150 秒挖开 (1,4)、(1,5)；从此时开始余额足够即在 (1,4) 建 Pantry。
- 300 秒挖开 (6,3)、(6,2)，接通 Sugar Drop。
- 360 秒挖开 (6,4)、(6,5)、(6,6)、(7,6)，接通 Sap Root。

当前基准结束状态：24 只成年蚂蚁、0 个卵、库存 1100/1100、累计搬入 1530、累计支出 430、补给刷新 2 次。守恒：1530 − 430 = 1100。430 包括新增 19 只×20 和首次建仓 50；这条快速饱和轨迹不能外推日留存或八天进度。

在仓库根目录运行，要求 Python 3.11+，仅标准库。每个命令失败必须返回非零退出码：

```bash
python -m unittest discover -s tests -v
python tools/economy_sim.py --check

python tools/check_strings.py
```

`python tools/economy_sim.py --tables` 输出运输对照；`--json` 输出机器可读对照和完整回放结果。旧 `--ads`、`--crew`、`--casual`、`--layout` 预测入口已撤回，不再输出付费优势或八天成长估计。

数值验收涵盖：三个手算对照；跨源共享路段；未连接不采集；同状态确定性、逐次分流改善和迭代上限；全挖地图下 1–24 只均可求解；满仓不扣粮；部分空间只扣实际入库；有限源不为负；反复补给；真实建仓合法性/费用/移动增益；人口与孵化槽；暂停攒钱；离线一致性与一小时封顶；资源守恒。

地图检查覆盖尺寸、符号、房间与补给占地、初始房间连通、潜在挖掘可达性以及 2×2 建仓空间。文案检查覆盖重复/缺失 ID、英文列混入中文和占位符替换后的长度。它不替代真机文字裁切检查。

### 6.4 客户端与试玩验收（待实现后验证）

- 三组夹具产量误差不超过 1e-5 Food/min，路线人数之和等于分配人数；新状态一个逻辑步内生效。
- 真实地图上挖格、建仓、取消、移动、暂停孵化可反复操作，无重复扣费/重复收入。
- 杀进程、后台一小时、后台两小时、系统时间回拨、存档损坏都不产生负数或额外离线奖励。
- 英文文案在目标 iPhone 的默认及较大文字设置中可读；关键按钮点击区域至少 44pt，不能被安全区遮挡。
- 以首版人口上限和全挖地图在选定最低支持机型录制性能；初定目标 60fps、无连续卡顿。机型和实测结果必须记录，Python 测试不能替代真机证明。

## 7. 验证指标与继续开发门槛

先做约 8–12 人有观察的测试，每人约 10–15 分钟。以下是项目决策门槛假设，不是行业基准或统计证明：多数人（目标至少 70%）无需口头指导即可接通第一处补给；至少一半能独立完成一次有效运输改善，并能说明原因；至少一半在主目标结束后主动再尝试一处布局。未达成时先调整核心交互和反馈，再考虑扩张内容。

### 7.1 埋点与判定

| 事件 | 记录内容 | 用途 |
|---|---|---|
| `first_source_connected` | 源 ID、用时、挖格数 | 接通理解，不等于优化 |
| `route_edit` | 挖格/建仓/移动、前后几何、同源固定人口下的预计产量 | 评估布局变化 |
| `route_improved` | 同一已连接源、同人口/速度/载量下的增益≥5% | 排除人口增长和新源切换 |
| `food_source_changed` | 旧源/新源、耗尽/补给/连接原因 | 解释收入变化 |
| `hatching_toggled` | 暂停/恢复、余额 | 检查是否理解攒钱 |
| `storage_full` | 时刻、容量、蚂蚁数 | 检查早饱和，而非付费触发 |
| `session_end` | 完成阶段、手动操作数、主动尝试次数 | 结合访谈判断继续意愿 |

对 route_edit 同时冻结两套场景的人口、源、载量、速度和孵化状态重新求解；来源从未连接变成连接时只记探索，不能算优化。Pantry 增加容量本身也不记路线改善；只比较运输几何。反馈即时展示，5% 阈值仅用于指标降噪，不是分流门槛。

停留时长、无输入时长不能证明“看蚂蚁很有趣”。观察兴趣必须结合当场行为、主动缩放/选中与访谈说明。没有付费产品的核心验证版不测付费转化率、广告收入或 LTV。

### 7.2 明确的失败条件

若挖土有反馈但玩家持续忽视运输，先优化路线可读性与结果比较；若挖完即无选择，先验证多目标摆放/新地图是否必要；若拥堵求解收益在真实地图中过少，先改地图或预算参数，并保留固定对照防回归。不得直接用增加等待、广告或商店来掩盖这些问题。

## 8. 开发拆分与后续商业验证

计划以小团队 2–4 周核心原型为估算，具体取决于客户端基础与美术资源，不是已确认工期。

| 阶段 | 交付 | 出口条件 |
|---|---|---|
| 第一阶段 | 格网、挖土触感、实体与路径展示 | 真机操作顺畅；固定路径夹具通过 |
| 第二阶段 | 拥堵/分流、孵化、仓库、补给 | 经济基准一致；完整首局可玩 |
| 第三阶段 | 存档、离线、英文 UI、埋点 | 生命周期与文案验收通过 |
| 第四阶段 | 观察试玩、问题修正、是否继续的决定 | 第 7 章形成实际证据 |

首版不接支付和广告。进入下一阶段后，先单独验证一个可选广告奖励和一个外观商品，定义触发、奖励、频次、非付费体验与对照实验，再建立商业模型。旧“只模拟 Double It 却代表全部广告”和“额外施工队提升成长”的结论撤回。收入、成本与获客假设需要实际数据，不能承诺每个游戏赚一亿。

尚未确认的事项：最低支持 iPhone 与 iOS 版本；最终引擎与美术管线；工作名可用性；试玩招募；达到人口/容量上限后的可持续目标。上述事项不妨碍本仓库先锁定并验证核心规则。
